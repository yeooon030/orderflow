# 테스트 결과를 신뢰하는 기준

## 문제

`./gradlew test`가 `BUILD SUCCESSFUL`을 출력해도 그것이 "검증됐다"를 뜻하지 않는다.

Day 1~3 동안 테스트 결과를 그대로 받아들여 잘못 판단한 사례가 3건 있었다.
세 건 모두 결과 자체는 정상이었고, **결과가 무엇을 보장하는지 확인하지 않은 것**이 원인이었다.

- 통과했지만 새로운 정보를 주지 않는 테스트를 유효한 검증으로 간주
- 통과했지만 DB에 남아 있던 상태 때문에 통과한 것을 정상 동작으로 간주
- 실패했지만 실패 원인을 확인하지 않고 의도한 원인으로 실패했다고 간주

이 프로젝트는 동시성과 성능을 다루므로, 테스트가 실제로 무엇을 잡는지 알지 못하면
이후 Lock 검증과 성능 측정의 근거가 전부 흔들린다.

## 선택지

| | 방식 | 내용 |
|---|---|---|
| A | 통과를 그대로 신뢰 | 추가 작업 없음 |
| B | 커버리지 도구 도입 | JaCoCo 등으로 실행 비율을 수치화 |
| C | 역검증 | 테스트가 잡아야 할 대상을 고의로 깨뜨려 실패하는지 확인 |

## 비교 기준

- 위 3건과 같은 오판을 실제로 잡아내는가
- 새로운 의존성이 필요한가
- 개인 프로젝트 기간 안에서 계속 유지할 수 있는가

## 선택

**C — 역검증.** 새 도구를 추가하지 않고 기존 Gradle과 psql로 수행한다.

## 선택 이유

B(커버리지)는 위 3건 중 어느 것도 잡지 못한다.
커버리지는 코드가 **실행됐는지**를 알려주고 **검증됐는지**는 알려주지 않는다.

세 사례 모두 해당 코드는 실행됐고 커버리지는 올라갔을 것이다.
문제는 단언(assertion)이 실제로 무언가를 붙잡고 있느냐였다.

C는 "이 테스트가 실패해야 하는 상황"을 직접 만들어 확인하므로,
단언이 비어 있거나 조건에 의존하는 경우를 드러낸다.
새 의존성이 없고, 확인이 필요한 시점에만 수행하므로 유지 비용도 없다.

## 검증 결과

### 사례 1 — 통과했지만 새로운 정보가 없던 테스트

Repository 5개를 만든 뒤 빈 등록과 테이블 매핑을 확인하는 테스트를 추가했고 통과했다.

의심한 것: 기존 `contextLoads()`가 이미 같은 것을 확인하고 있지 않은가.

확인 방법: `UserRepository`에 존재하지 않는 필드를 참조하는 메서드를 넣고
`contextLoads()`만 실행했다.

```text
OrderFlowApplicationTests > contextLoads() FAILED
  Caused by: QueryCreationException
    Caused by: PropertyReferenceException
```

결과: Spring Data는 컨텍스트 기동 시점에 Repository 빈을 생성하므로
`contextLoads()` 하나로 이미 실패한다. 추가한 테스트는 결함 검출 면에서 중복이었다.

이 테스트는 삭제하지 않고 남겼다. 결함 검출이 아니라
**JUnit 리포트에 무엇을 확인했는지 남기는 용도**로 유지한다는 것을 분명히 한 상태다.

### 사례 2 — DB에 남은 상태 때문에 통과한 테스트

테스트용 Seed가 id를 직접 지정하므로 시퀀스를 그 뒤로 밀어야 한다.
`setval` 구문이 정말 필요한지 확인하려고 지우고 실행했더니 **통과**했다.

의심한 것: 필요 없다는 결론이 나왔는데, 없어도 되는 이유를 설명할 수 없었다.

확인 방법: 시퀀스 현재 값을 조회하니 `last_value = 150`이었다.
앞선 실행들이 이미 시퀀스를 올려놓은 상태였다. 초기 상태로 되돌리고 다시 실행했다.

```bash
docker exec orderflow-postgres psql -U orderflow -d orderflow \
  -c "ALTER SEQUENCE users_seq RESTART;"
```

```text
Seed_이후_JPA로_저장해도_PK가_충돌하지_않는다() FAILED
  Caused by: ConstraintViolationException
```

결과: **시퀀스 값은 트랜잭션 롤백 대상이 아니다.**
테스트가 롤백되어도 시퀀스는 되돌아가지 않고 DB에 상태가 남는다.
시퀀스가 얽힌 테스트는 초기 상태를 만들지 않으면 통과를 신뢰할 수 없다.

이 과정에서 Seed의 `setval`이 매 테스트마다 시퀀스를 되감아
Hibernate가 확보한 구간과 겹치는 결함도 함께 발견했다.
자세한 내용은 `sequence-allocation-size.md`에 있다.

### 사례 3 — 실패했지만 원인이 달랐던 테스트

`INCREMENT BY`와 `allocationSize` 불일치를 재현하려고 DB 시퀀스만 바꿔 실행했고,
테스트 3건이 전부 실패했다. 이를 "테스트가 불일치로 인한 PK 충돌을 잡았다"고 기록했다.

의심한 것: 실패했다는 사실만 보고 실패 **원인**을 확인하지 않았다.

확인 방법: 결과 XML에서 스택트레이스를 열었다.

```text
Caused by: org.hibernate.MappingException: The increment size of the
[users_seq] sequence is set to [50] in the entity mapping while the
associated database sequence increment size is [1]
```

결과: PK 충돌이 아니라 **EntityManagerFactory 생성 실패**였다.
테스트는 실행조차 되지 않았다. Hibernate 6.6.53은 `ddl-auto: validate`에서
시퀀스 increment까지 검증한다.

기존 문서(BACKEND.md)에 있던 "`ddl-auto: validate`는 이를 검증하지 않는다"는
서술도 이 과정에서 사실과 다른 것이 확인되어 수정했다.

## 적용 방법

이후 작업에서 다음을 지킨다.

**통과했을 때**

- 결과 XML에서 `skipped="0"`을 확인한다. 스킵돼도 빌드는 성공한다.

  ```bash
  grep -o 'tests="[0-9]*" skipped="[0-9]*" failures="[0-9]*" errors="[0-9]*"' \
    build/test-results/test/*.xml
  ```

- 새로 추가한 테스트는 **한 번은 실패시켜 본다.** 검증 대상을 고의로 깨뜨렸을 때
  실패하지 않으면 그 테스트는 아무것도 붙잡고 있지 않다.
- 기존 테스트로 이미 잡히는 것은 아닌지 확인한다.

**실패했을 때**

- "실패했다"로 결론 내지 않고 스택트레이스에서 원인을 확인한다.
  의도한 원인과 다른 이유로 실패했을 수 있다.

**DB 상태에 의존하는 테스트**

- 시퀀스처럼 롤백되지 않는 상태는 확인 전에 초기화한다.
- 저장 건수가 적은 테스트는 이미 확보된 자원 안에서 끝나 재할당 경로를 지나지 않는다.
  경계를 넘기는 건수를 사용한다.

## 이후 적용 대상

Day 4~5 동시성 테스트가 이 기준의 주요 적용 대상이다.

Pessimistic Lock은 적용 여부를 코드만으로 판단할 수 없다.
Lock을 제거했을 때 동시성 테스트가 실제로 실패하는지 확인해야
그 테스트가 Lock을 검증하고 있다고 말할 수 있다.
